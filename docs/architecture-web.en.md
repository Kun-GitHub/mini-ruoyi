# Frontend architecture

English | [简体中文](architecture-web.md)

Svelte 5 + Vite + TypeScript + Tailwind CSS v4 + shadcn-svelte.
A purely static single-page application whose output is hosted from disk by the backend — **SvelteKit is not used**.

## 1. Technology choices

| Item | Version | Notes |
| --- | --- | --- |
| Svelte | 5.57 | Uses runes (`$state` / `$derived` / `$props`), not the old `export let` / stores |
| Vite | 8.3 | Build and dev server |
| TypeScript | 6.0 | TypeScript throughout, including type checking inside `.svelte` |
| Tailwind CSS | 4.3 | v4's CSS-first configuration, no `tailwind.config.js` |
| shadcn-svelte | 1.7 | Components are **copied into the repository**, not a runtime dependency |
| bits-ui | 2.19 | The headless foundation under shadcn-svelte |
| lucide | — | Icon library (declared in `components.json`) |

### Why not SvelteKit

What we want is "static output hosted by the backend". SvelteKit's SSR and Node adapters are pure overhead in that
shape, and `adapter-static` with `ssr=false` only adds the complexity back. So: Vite + Svelte directly, with routing
written by hand.

### Why shadcn-svelte for components

Component source is copied into `src/lib/components/ui/` — it is **not a dependency package**. Therefore:

- Only the components actually used are bundled; there is no "import one library, ship all of it" problem
- Components can be restyled freely, with no upstream API constraints
- There is no risk of a breaking change on a version upgrade

The price is that components do not automatically receive upstream fixes; updating means running
`npx shadcn-svelte add <component> --overwrite` by hand.

The `$lib` alias points at `src/lib` and is declared both in `vite.config.ts` (resolution by Vite) and in
`tsconfig.json` / `tsconfig.app.json` (resolution by TypeScript and validation by the shadcn CLI). Neither can be
omitted.

> Do **not** add `baseUrl` to `tsconfig.json`. `paths` works on its own from TS 4.4, and `baseUrl` is removed in TS 7.0
> (`svelte-check` reports a deprecation warning).

## 3. Svelte 5 reactivity conventions

Runes, not the old syntax.

| Situation | Syntax |
| --- | --- |
| Component-internal state | `let count = $state(0)` |
| Derived values | `const doubled = $derived(count * 2)` |
| Side effects | `$effect(() => { ... })` |
| Component props | `let { title, children } = $props()` |
| Two-way binding to a component | `bind:value` + `$bindable()` |

**No state-management library.** Runes are themselves the reactivity system, and Vue's Pinia / Vuex have no
corresponding need here. Shared state across components is a `.svelte.ts` module exporting getters/setters (see the i18n
implementation in §4).

**No axios.** Native `fetch` plus a thin wrapper is enough; see §5.

## 4. i18n

Hand-written, about 130 lines, **zero runtime dependencies**.

```
src/lib/i18n/
├── zh-CN.ts          # the single source of truth, as const (310 keys today)
├── en-US.ts          # Record<keyof typeof zhCN, string> → a missing key is a compile error
├── index.svelte.ts   # locale state ($state) + t() + persistence
└── errors.ts         # the single rendering path for field-level errors: fieldLabel() + validationText() + fieldErrorOf()
```

### 4.1 Why not a library

There are only two locales and a small message count. The dynamic loading and date/number formatting plugins that
runtime libraries like `svelte-i18n` bring are all unused here — native `Intl.*` covers dates and numbers. The
hand-written version also gets you: nothing but the strings themselves in the output, and **a missing key as a compile
error** (measured: delete one key from `en-US.ts` and `npm run check` immediately reports
`Property '"error.notFound"' is missing in type ... but required in type 'Record<...>'`).

Switch to paraglide-js (compile-time generation, tree-shaking per message) when the message count reaches the hundreds
and per-route chunks are needed.

### 4.2 Reactive locale switching

```ts
// A module-level $state cannot be exported as a mutable binding, so only getters/setters leave the module
let current = $state<Locale>(initialLocale())

export function getLocale(): Locale { return current }
export function setLocale(next: Locale) { ... }

export function t(key: MessageKey, params?): string {
  const template = dicts[current][key] ?? key   // ← reads $state, so the template tracks it automatically
  ...
}
```

Because `t()` reads `$state`, calling `t('...')` inside a template establishes a dependency and `setLocale()`
re-renders automatically, with no page refresh.

### 4.3 Locale resolution and persistence

```
localStorage['mini-ruoyi.locale'] present and in the supported list → use it
otherwise navigator.language starts with "zh"                      → zh-CN
otherwise                                                          → en-US
```

Switching locale writes to both localStorage and `document.documentElement.lang`.

### 4.4 The key convention with the backend

The backend only emits i18n keys (see [architecture-server.en.md](architecture-server.en.md)); the frontend dictionary
does the translating. **A new error key means changing two places**:

- the key constant in `server/internal/httpx/response.go`
- `web/src/lib/i18n/zh-CN.ts` (a missing key in `en-US.ts` is a type error, so it cannot be forgotten)

### 4.5 Rendering field-level validation errors

The backend only supplies `{field, rule, param}` and the frontend assembles the text: the rule becomes the dictionary key
`validation.<rule>`, and **an unimplemented rule falls back to `validation.default`**, so a new backend rule cannot break
the UI.

All of that logic is collected in `i18n/errors.ts`:

| Function | Responsibility |
| --- | --- |
| `fieldLabel(field)` | field name → message key, looked up in `fieldLabelKeys`; **an unknown field falls back to the field name itself** |
| `validationText(fe)` | one error → displayable text |
| `fieldErrorOf(errors, field)` | the message for a given field, or `null` (used directly in `{#if}` in templates) |

All four pages that show form errors (`profile` / `users` / `roles` / `menus`) call only `fieldErrorOf()`.
This used to be four hand-written copies of `fieldError()`, each assembling a field label with
`tKey(\`field.${field}\`)` — and `tKey()` **returns the key name unchanged** when it cannot find it, so an unknown field
was displayed as `field.new_password不能为空`.

That gap is now closed by the backend case `TestFrontendDictCoversFieldNames`: it scans every json field name carrying a
`binding` tag in `handler/*.go` and asserts that `fieldLabelKeys` and both dictionaries have a message for each one. Add
a validation field and forget the copy, and `make test` goes red.

## 5. Integration with the backend

### 5.1 The response contract

The backend always returns (details in [architecture.en.md](architecture.en.md)):

```jsonc
{ "code": 200, "msg": "ok", "data": {...} }
{ "code": 400, "msg": "error.validationFailed", "errors": [{ "field", "rule", "param" }] }
```

How the frontend consumes it:

- Success is decided by the **HTTP status code** (`res.ok`), never by `code`
- `code` is used only to discriminate "is this our envelope": if it is not a number the client reports
  `error.backendUnreachable` (the Vite proxy returns 502 with an empty body when the backend is down, and this is what
  separates that from "the backend errored")
- On failure `msg` is an i18n key, rendered directly through `t(msg)`
- When `errors[]` is present, the corresponding form fields are highlighted

### 5.2 The API client

`src/lib/api/client.ts` is the single entry point for every call. Its responsibilities:

| Responsibility | Notes |
| --- | --- |
| Unwrap the envelope uniformly | Returns `data` on success and throws `ApiError` on failure (carrying `key`, `fieldErrors`, `dependents`) |
| CSRF injection | Non-GET requests automatically carry `X-CSRF-Token`, whose value session state sets at login and on refresh |
| 401 handling | The callback registered via `setUnauthorizedHandler` clears session state and returns to the login page |
| Network failures | `fetch` itself throwing → `error.network` |
| A non-envelope response | Treated as `error.backendUnreachable`, see §5.4 |
| multipart | A separate `api.upload()`: **Content-Type must not be set**, because the browser has to generate the boundary |

The dependency between session state (`stores/session.svelte.ts`) and the client is **one-way**: the client knows nothing
about business state and only calls back on a 401. That keeps the client independently testable and avoids a circular
dependency through the store.

### 5.3 Self-healing when a static asset fails to load

```ts
// src/main.ts
window.addEventListener('vite:preloadError', () => location.reload())
```

The backend hosts the output directly, so rebuilding the frontend removes the old hashed files. An already-open tab that
lazily loads anything then hits a 404; this reloads the whole page to pick up the latest version.

### 5.4 ⚠️ "The response is not the envelope" means the request never reached the backend

`client.ts` does not judge a response by "is the HTTP status 2xx" but by **"is this the envelope shape of this service"**
(`{code, msg, ...}`). That is because "the backend is not running" and "the backend errored" need completely different
investigations:

| Symptom | Verdict | Key |
| --- | --- | --- |
| `fetch` throws | Nothing answered at all (DNS, connection refused) | `error.network` |
| An HTTP response, but not the envelope | A proxy or gateway answered, or the backend process is not up | `error.backendUnreachable` |
| The envelope | The backend handled it normally; translate by `msg` | whatever key the backend supplied |

Measured: **when the backend is not running, the Vite dev server returns `502 Bad Gateway` + `text/plain` + an empty
body.** An early version classified that as `error.internal`, which made the UI say "internal server error" and sent
people digging through backend logs — for a backend that was never started.

The premise behind the judgement is that **any response coming from this service is always the envelope shape**. That is
why `middleware.Recovery()` replaces `gin.Recovery()`: the latter returns a 500 with an empty body, which breaks that
premise and violates the "every API response carries the envelope" contract.

### 5.5 Session and startup flow

`src/lib/stores/session.svelte.ts` holds the user, permission codes, menu tree and CSRF token.

```
startup → bootstrap() calls /auth/me
        ├ success → authenticated, enter the app shell
        └ failure → anonymous, show the login page (and normalize the address bar to /login)
```

**A page refresh has to ask `/auth/me` again**: the cookie is still there, but the CSRF token only lives in memory, and
without fetching it anew no write request can be sent.

There is only one way to check permission: `session.can('system:user:add')`. For a built-in administrator the backend
fills `perms` with every permission code, so the frontend needs no `isAdmin ||` style branches — one fewer place to get
the check wrong.

On a 401, `client.ts` calls the callback registered by `setUnauthorizedHandler` (namely `clear()`), which logs the user
out automatically. The client thus stays unaware of business state and the session logic stays in the store.

### 5.6 Routing

`src/lib/router.svelte.ts` is about 120 lines, with no routing library.

```
menu tree ──flatten──▶ [{ path, titleKey, component }]
                            │
browser path ──exact match──┘
                            ▼
              import.meta.glob('../pages/**/*.svelte') resolves component
```

- It uses `{ eager: true }`, so resolution is synchronous: no loading state and no blank flash when a menu item is
  clicked. That trade-off is worth it at a dozen-odd pages; switch to lazy loading with `{#await}` when it grows to
  dozens
- When `component` cannot be found it returns `null` and shows a clear message rather than **throwing**. The menu is data
  in the database which may have been edited by hand or may reference a page that was deleted — the user should be able
  to see what happened, not have the whole app crash so that even navigation stops working
- After login, if the current path is not in the menu, it `replaceTo`s the first reachable page

### Built-in routes

One class of page **does not come from the menu**: currently the personal centre (`/profile`). These are declared in
`builtinRoutes` inside `router.svelte.ts` and take part in routing and tabs exactly like menu pages, only with a
different source.

Why not make it a menu item: the menu is a **permission-management** construct (assignable, disableable, needs a
permission code), whereas "change my own password" is a basic capability of every account. Making it a menu item means
giving it a permission code, and an account with no permissions would fall back to "can do nothing at all".
Correspondingly, the backend's `/profile*` routes are `self` routes rather than `protect` routes.

### 5.7 Multiple tabs

`src/lib/stores/tabs.svelte.ts` only tracks "which tabs are open"; **which one is active is decided by the router**
(`route.pathname`). No second copy of `activePath` is kept, or browser back/forward and typing in the address bar would
bypass it.

The content area renders **every tab's page at once, hiding the inactive ones with CSS** (see `app-shell.svelte`). That
is the entire point of tabs: switching back preserves form contents, scroll position and already-loaded data. The price
is that more open pages means more live component instances — an admin panel's tab count is in the single digits, which
is acceptable.

Three traps that tests keep closed:

1. **Open a tab on a "path change", not on "the current path is a menu page".** The latter breaks "close all" — after
   closing, the path has not changed and the effect runs again and adds the tab back. The implementation records
   `lastOpened` in a plain variable (not `$state`, since changing it should not trigger a re-run).
2. **A page must not continuously read the global URL.** With tabs, the URL only reflects the active tab, so a hidden
   page that keeps following it has its own filters wiped when you switch tabs, and re-requests using someone else's
   parameters. So list pagination/filters are **component-local state**, read from the URL once at mount (a refresh still
   works) and written one-way. The price is that back/forward does not refill the filter inputs.
3. **E2E selectors must be scoped to the visible panel.** Every open tab is in the DOM (merely hidden), so a page's
   `data-testid` exists several times over — `getByTestId('filters')` matches multiple elements and trips Playwright's
   strict mode. `filters()` in `e2e/helpers.ts` is already scoped to `[data-testid="tab-panel"]:visible`.

### 5.8 ⚠️ A 409 is a confirmation signal, not an error

Deleting a resource that has child data returns `409 + error.hasDependents + the impact`.
**That is not an error**: the frontend must show a confirmation dialog, not an error toast.

The rule is wrapped in one place, `src/lib/api/delete.ts`:

```ts
const done = await deleteWithConfirm(`/menus/${id}`)
// inside: DELETE → on 409 show the confirm dialog → on confirmation DELETE ...?cascade=true
```

Get the order wrong and the user sees a red error first and a confirmation dialog second, with no idea what happened.
Every delete entry point has to go through this wrapper rather than calling `api.del` directly.

## 6. Styling and components

### 6.1 Tailwind v4

CSS-first configuration, with **no `tailwind.config.js`**. Theme variables are defined in `src/app.css`:

```css
@import "tailwindcss";
@import "tw-animate-css";
@import "shadcn-svelte/tailwind.css";
@import "@fontsource-variable/inter";

@custom-variant dark (&:is(.dark *));
:root { --background: oklch(...); --primary: oklch(...); ... }
```

To change the theme colours, edit the variables in `:root` directly. The variable block in `app.css` is generated by the
shadcn CLI, so running `init` again overwrites it (the CLI asks for confirmation).

### 6.2 Theme preset

`components.json` sets `"style": "mira"`, one of shadcn-svelte 1.7's eight presets:
**"Compact. Made for dense interfaces."** — admin panels are dense with tables and forms, so it is the right pick.

The other presets: `nova` (compact), `vega` (the classic shadcn look), `maia` (loose and rounded), `lyra` (square, with
a monospace pairing), `luma` (rounded with texture), `sera` (editorial typography), `rhea` (a compact luma).

To switch: change `style` in `components.json` and re-run `npx shadcn-svelte@latest init --reinstall`.

### 6.3 Adding a component

```bash
cd web
npx shadcn-svelte@latest add dialog select table
```

Components land in `src/lib/components/ui/<name>/` and can be modified freely. The CLI adds any necessary npm
dependencies itself.

### 6.4 Library or native element

The principle: **use a library only when it provides value that is hard to reproduce; anything that is purely styling uses
the platform's native elements.**

Measured (two builds of the same page):

| Approach | JS output size |
| --- | --- |
| shadcn's `select` + `checkbox` | 301 kB / **93.1 kB gzip** |
| native `<select>` / `<input type="checkbox">` | 215 kB / **71.4 kB gzip** |

Two dropdowns and a few checkboxes cost **about 22 kB gzip** extra, while native elements come with keyboard navigation,
mobile pickers and screen-reader support built in. Hence this project's choices:

| Use | Choice | Reason |
| --- | --- | --- |
| Dropdowns, checkboxes | **native elements** + Tailwind | The library only adds appearance, with no irreplaceable capability |
| Dialogs | **shadcn Dialog (bits-ui)** | Focus trapping, Esc to close, aria and the portal are easy to get wrong by hand |
| Tables | shadcn Table | Pure markup plus styling, at nearly zero runtime cost |

Run any new component past that standard before adding it; do not default to "if it exists, use it".

### 6.5 Form control sizing convention

Every form control takes its size from one source. **Do not hand-write heights.**

| Control | Component | Height |
| --- | --- | --- |
| Text input | `ui/input` (shadcn-generated) | `h-7` |
| Dropdown | `ui/native-select` (ours) | `h-7` |
| Button | `ui/button`'s `default` size | `h-7` |

`native-select` is our own component rather than shadcn's `Select`: the latter is built on bits-ui and costs about
20 kB gzip extra, while native keyboard navigation, mobile pickers and screen-reader support are already sufficient.

**A trap we hit**: heights were once hand-written all over the place as `<select class="h-9 ...">` while `Input` was
`h-7`, so in the filter bars "the text box was a notch shorter than the dropdown". Sharing a component makes that
impossible — and `e2e/form-controls.spec.ts` **measures pixel heights in a real browser** to keep the inconsistency from
coming back after a theme preset change or a shadcn component upgrade.

### 6.6 Filter bar layout

Fields use a **fixed width plus wrapping** (`flex flex-wrap items-end gap-3`, fields at `w-48`), not an equal-width grid:

- Equal columns (`grid sm:grid-cols-4`) stretch inputs very wide on a large screen, which makes scanning harder
- With a fixed width, a wider screen simply fits more fields and the visual density stays constant
- Buttons (search/reset) wrap along with the fields rather than being pushed to the far right — with fixed widths that
  leaves a large gap in the middle

`e2e/form-controls.spec.ts` pins both of these down: field width does not change with the viewport, and a narrow screen
wraps instead of squashing.

| Package | Why it is here |

| `bits-ui` | The headless foundation under shadcn-svelte; the current components do not reference it directly, but interactive ones (dialog/select/dropdown) depend on it |
| `tailwind-variants` | Referenced by button / badge to generate variant classes |

## 7. Build output and backend integration

```
vite.config.ts
  build.outDir    = 'dist'        # output lands in web/dist
  build.assetsDir = 'assets'      # assets land in dist/assets/ ← must line up with the backend's /assets/ prefix
```

The backend takes over by directory convention (see [architecture-server.en.md](architecture-server.en.md)):

```
web/dist/index.html   →  service root, Cache-Control: no-cache
web/dist/assets/*     →  /assets/*, Cache-Control: immutable
```

**Current output size** (measured, including i18n, login, the app shell and all 11 business pages):

| File | Raw | gzip |
| --- | --- | --- |
| `index.html` | 0.5 KB | 0.3 KB |
| `assets/index-*.css` | 42.7 KB | 8.2 KB |
| `assets/index-*.js` | 312 KB | **89 KB** |
| `assets/*.woff2` (every Inter variable subset) | 213 KB | — |
| Total (12 files) | 583 KB | — |

The font is the largest single piece. For Chinese and English only it could be trimmed to the latin + latin-ext subsets.

These numbers come from a fresh `make web`. **They drift a little with every build** (the content hashes in the filenames
change each time), so use them to judge the magnitude and which piece dominates — not as an exact baseline to diff against.

### 9.1 How verification works

Three layers, each with its own job:

| Layer | Command | Coverage |
| --- | --- | --- |
| Types and templates | `npm run check` | svelte-check + tsc |
| Interface contract | `make test` | the backend's 130 cases (all correctness unrelated to CGO lives here) |
| Real interaction | `make test-e2e` | Playwright + Chromium, 11 specs / 81 cases |

E2E goes through `webServer`, which automatically starts **a backend on a temporary database**, clearing it before every
run — leftover data turns assertions like "N rows in total" into things that depend on execution order, which is very
hard to debug. Tests run serially (`workers: 1`) because they share one database.

Two lessons from writing E2E:

- **Notifications stack**, so `getByText('已保存')` matches the one left by the previous operation and lets the assertion
  pass even when the request failed. To assert "the save succeeded", assert that **the dialog closed**.
- **Buttons with identical labels interfere with each other** (the sidebar versus the tab bar, a filter bar versus a
  dialog), so `data-testid` must scope the query or Playwright's strict mode trips.

Real defects E2E has already caught: the roles checked when creating a user being silently dropped
(`if (form.id !== null)` missed the create path), and tabs coming back by themselves after "close all".
